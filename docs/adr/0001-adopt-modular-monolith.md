## ステータス

承認済み

## コンテキスト

kalos は Rust 製 CLI ツールとして、複数言語のソースコードを解析し、CPG 抽出から診断出力までを一貫して実行する必要がある。要件では以下が強く求められている。

- 単一バイナリ配布 (`REQ-FUNC-031`)
- GitHub Actions などから簡単に呼び出せること (`REQ-FUNC-032`)
- 全解析 60 秒以内、差分解析 10 秒以内 (`REQ-NF-001`, `REQ-NF-002`)
- ビット単位の決定論性 (`REQ-NF-003`)

一方で、ドメインモデルは `CPG抽出 / 差分解析 / メトリクス算出 / 診断 / 構成管理 / レポート` の明確な境界を前提としている。加えて、解析パイプラインは `CPG → Metrics → Diagnostics → Report` の依存チェーンに従い、差分解析/ベースライン再利用はこの直列パイプラインを横断する内部サービスとして ADR-0003 に分離して扱う必要がある。外部エンジン（CodeQL）や将来の代替エンジンを差し替え可能にする必要もある。

## 検討した選択肢

### プロセス分割の選択肢

#### 選択肢 A: 単一バイナリのモジュラーモノリス

1 プロセスの中でコンテキストごとにモジュール境界を持つ構成。

- 利点:
  - 配布と実行が単純
  - 決定論性を制御しやすい
  - CPG から診断までの中間データをプロセス内で扱える
- 欠点:
  - 巨大化すると境界が崩れやすい
  - 一部機能だけの独立デプロイはできない

#### 選択肢 B: マイクロサービス群

抽出・計算・診断を別プロセス/別サービスに分割する構成。

- 利点:
  - 個別スケールや独立デプロイができる
  - 技術選定を分離しやすい
- 欠点:
  - CLI ツールとしては運用コストが過剰
  - 決定論性と配布容易性を損ないやすい

#### 選択肢 C: プラグイン中心のマイクロカーネル

最小コアと多数の動的プラグインで構成する。

- 利点:
  - 拡張点を増やしやすい
  - 実験機能の差し込みがしやすい
- 欠点:
  - 初期リリースには複雑すぎる
  - 性能とトラブルシュートが難しくなる

### 内部構成パターンの選択肢

プロセス分割として選択肢 A（モジュラーモノリス）を採用する前提で、モノリス内部をどのように構成するかについても複数案を検討した。

#### 選択肢 A-1: レイヤードアーキテクチャ（モジュラーモノリス + 従来型の層構成）

Presentation / Application / Domain / Infrastructure の水平層でモジュールを分割する。

- 利点:
  - 構造が単純で馴染みやすい
  - フレームワークのサンプルが豊富
- 欠点:
  - 外部依存（CodeQL、LLM）の差し替えが層をまたぐ変更になりやすい
  - ドメイン層がインフラ層の詳細に引きずられやすい

#### 選択肢 A-2: Ports & Adapters + Pipe-and-Filter（採用案）

外部依存を Port/Adapter で隠蔽し、解析パイプラインを直列ステージ構成で表現する。

- 利点:
  - 外部エンジン差し替えがアダプタ層の変更に閉じる
  - ステージ単位のベンチマーク・キャッシュ・障害切り分けが容易
- 欠点:
  - Port/Adapter の設計・保守コストが追加される
  - ステージ間のデータ受け渡しに明示的な契約設計が必要

#### 選択肢 A-3: モジュラーモノリス（Pipe-and-Filter なし）

Ports & Adapters は採用するが、パイプライン構成は Application 層の手続き的なオーケストレーションに委ねる。

- 利点:
  - 直列ステージの抽象化が不要で初期実装が軽い
- 欠点:
  - ステージ境界が暗黙的になり、プロファイリングやキャッシュ挿入点の設計が曖昧になる
  - 差分解析/ベースライン再利用の横断的関心事をどこに置くか判断しづらい

## 判断

選択肢 A を採用する。さらに、モノリス内部の構成パターンとして **Ports & Adapters**（Hexagonal Architecture）と **Pipe-and-Filter** を組み合わせて用いる。

## 根拠

### モジュラーモノリスの採用

- CLI 製品では、分散境界よりも単一バイナリ配布の価値が高い
- `REQ-NF-003` の決定論性は、プロセス間通信を減らすほど実現しやすい
- ドメイン境界はマイクロサービスではなく、モジュール境界として維持すれば十分である

### 内部構成パターンの選択（選択肢 A-2 を採用）

レイヤードアーキテクチャ（A-1）は構造が単純だが、CodeQL や将来の代替エンジンの差し替えが層をまたぐ変更になるため、ADR-0002 以降の差し替え可能性要件と相性が悪い。Pipe-and-Filter なし（A-3）は初期実装が軽いが、差分解析のキャッシュ挿入点やステージ単位のベンチマークが暗黙的になり、`REQ-NF-001`/`REQ-NF-002` の性能検証を難しくする。

- **Ports & Adapters**: 外部エンジン（CodeQL）や将来の代替エンジン、LLM、キャッシュストレージなどの外部依存を Port の背後に閉じ込め、ADR-0002/0004/0005 の差し替え可能性を実現する
- **Pipe-and-Filter**: 要件文書の依存チェーン `CPG → Metrics → Diagnostics → Report` をステージの直列構成として表現し、ステージごとのベンチマーク・キャッシュ・障害切り分けを容易にする
- **差分解析/ベースラインの位置づけ**: ADR-0003 で定義する `Impact Analysis Service` と `Baseline Cache Adapter` は、上記パイプラインを補助する横断サービスとして Application Pipeline が統制する。それぞれ独立したコンポーネント（`Impact Analysis Service` は内部サービス、`Baseline Cache Adapter` は `Baseline Cache Port` を実装するアダプタ）として配置し、独立したアーキテクチャ層へ昇格はさせない（architecture.md §4.1 参照）

## 帰結

### ポジティブ

- リリース・配布・CI 統合が単純になる
  - **保証範囲**: 「単一バイナリ」は kalos 実行ファイル自体を指す。CodeQL bundle および WASM プラグインは kalos バイナリに同梱されない外部アーティファクトであり、責務の範囲が異なる:
    - **CodeQL bundle**（ADR-0002）: Managed Tool Cache Adapter が取得（初回 bootstrap）・checksum 検証・ローカルキャッシュの全ライフサイクルを担う。ユーザーは手動で配置する必要がない
    - **WASM プラグイン**（ADR-0004）: ユーザーがワークスペースに配置し、`.kalos.toml` の `[[plugins]] { path, sha256 }` で登録する。kalos は `sha256` checksum 検証と SPI version 検証を行うが、取得・配布は行わない
    - 配布物としてはバイナリ単体を単位とする
- ベンチマーク、スナップショットテスト、順序固定を一貫して適用できる
- ドメインモデルの境界をコード構造へ直接反映しやすい
- Ports & Adapters により外部依存（抽出エンジン、LLM、キャッシュ）を差し替え可能に保てる
- Pipe-and-Filter によりステージ単位でのプロファイリングと障害切り分けが容易になる

### ネガティブ

- 依存方向を破るとすぐに Big Ball of Mud 化する
- 一部の重い処理を独立スケールさせにくい

### リスク

- モジュール境界が曖昧化するリスクがあるため、アーキテクチャテストで循環依存を禁止する
- 無循環であっても依存方向の逆流（例: `domains` → `adapters`）は Hexagonal Architecture の原則に反する。許可する依存方向は以下の通りとし、`architecture.md` の「適合度関数: モジュール依存 DAG」で定義するアーキテクチャテストで強制する:
  - `application` → `domains`, `ports`
  - `application` → `adapters`（コンポジションルートとしての具象アダプタ選択・初期化に限定。ドメインロジックからアダプタへの直接依存ではない）
  - `adapters` → `ports`
  - `domains` → `ports`（ポートインターフェースおよび Published Language 型の参照。ドメインがポート定義に依存するのは Hexagonal Architecture の正規の依存方向である）
  - `domains` 間は公開契約（Port 経由）でのみ接続する
  - **公開契約型の配置**: コンテキスト間で共有する Published Language 型（domain_model.md §2 コンテキストマップの PL。例: `SourceAnalysis`、`ScopeMetrics`）は `ports` モジュールに定義する。上記 `domains` → `ports` および `adapters` → `ports` により、双方から参照可能な唯一の共有配置場所となる。この配置ルールは [architecture.md §4.2](../architecture.md)（依存方向）で実施され、ADR-0003 / ADR-0004 の共有契約型もこのルールに従う
  - `domains` → `adapters` の直接依存、`adapters` → `domains` の直接依存は禁止する
